# Syntyr design contract

This is the **portable, agent-readable visual design contract** for Syntyr CSS.
The frontmatter follows the [Google DESIGN.md alpha format](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md). It describes the **Studio reference palette**, not every theme. The CSS source is authoritative; this snapshot is derived and checked automatically. The YAML values are not a second configuration system.

## Token source of truth

- The published CSS custom-property API is `--syn-*`. Read `src/tokens.css` for primitive colors, spacing, typography, geometry, density, and theme overrides. Read `src/base.css` for baseline semantics and `src/components/` for component implementations.
- For runtime behavior, compiled distributions in `dist/` are generated by `python3 scripts/build.py`. **Never** hand-edit built CSS, introduce a JavaScript theme configuration, or make this YAML control the runtime.
- Run `python3 scripts/sync_design_md.py` after changing relevant Studio or base tokens. Run `python3 scripts/sync_design_md.py --check` in review/CI. The generation and checks use Python's standard library only.
- The DESIGN.md spec is currently alpha and models one palette. Other palettes, computed `color-mix()` roles, media-query values, motion timings, intensity, density, and state variants stay in CSS. Do **not** assume that exporting this frontmatter reproduces the entire library.
- In the YAML, `spacing.xs` through `spacing.xl` correspond to `--syn-space-1` through `--syn-space-5`; `rounded.default` corresponds to Studio `--syn-radius`. Color token names are semantic aliases for `--syn-*` values. Components entries illustrate intended role pairings, not exhaustive component CSS.

For cross-design-system conventions, component-state expectations, native composition recipes and the executable palette audit, see [the design principles guide](docs/design-principles.md).

## Design principles and precedence

1. **Information before decoration.** Prioritize readable content, hierarchy, meaningful affordances, and stable layout over visual effects.
2. **Web-native before custom.** HTML semantics, native form controls and the platform's state machinery come before custom widgets.
3. **Neutral by default; personality by opt-in.** Studio is the professional light default; Grid/Noir and other themes are named palette options, not mandatory sci-fi styling.
4. **Accessible interaction is non-negotiable.** Contrast, keyboard navigation, focus indication, zoom/reflow and reduced motion take precedence over visual fidelity.
5. **Independent axes.** Palette, density, geometry, intensity and typography must remain independently composable. Changing one should not silently change another.
6. **Low maintenance, low coupling.** CSS custom properties and scoped classes are the stable integration surface. No framework, remote font, runtime service or asset CDN is required.
7. **Original identity.** Do not copy proprietary logos, fonts, assets, distinctive brand combinations, screenshots, or trade dress from Oxide, Linear, Resend, TRON, Blade Runner or other references.

## Palette, surface, and type hierarchy

- **Studio** (`data-syn-theme="studio"`, also the default): low-noise professional SaaS surfaces, readable body type, clear primary action, subdued secondary emphasis. The generated YAML above captures its static baseline.
- **Grid** (`data-syn-theme="grid"`): dark technical dashboards with high-contrast cyan accents. Apply precision graphics sparingly.
- **Noir** (`data-syn-theme="noir"`): warm cinematic/editorial presentations with amber accent, not a universal default.
- **Industrial, Terminal, Corporate, Minimal**: additional candidate palettes in unreleased alpha.5; do not promise them in the published alpha.4 release. Follow actual source and tagged release availability.
- **Auto** (`data-syn-theme="auto"`): experimental native system color-scheme path; confirm both scheme outcomes and nested theme boundaries before deployment.

Use `--syn-bg` for page, `--syn-surface` for cards, `--syn-surface-hi` for more prominent surfaces, `--syn-frame` for standard borders, `--syn-frame-strong` for structural emphasis, `--syn-text` for primary content, and `--syn-muted` for secondary content. Where available, prefer derived semantic roles `--syn-surface-raised`, `--syn-border-subtle`, `--syn-border-focus`, and `--syn-focus-ring` over manually mixed colors.

Use `--syn-font` and `--syn-font-ui` for normal interfaces; reserve `--syn-mono` for terminal, numeric and technical elements. Use `--syn-type-body`, `--syn-type-heading`, `--syn-type-section`, and `--syn-type-display` by content hierarchy, not purely visual preference. Default to system fonts; custom fonts are optional.

## Component and state contract

| Purpose | Existing Syntyr hook | Required behavior |
| --- | --- | --- |
| Scope | `.syn-root` | No unintended styling of siblings outside the root |
| Theme boundary | `data-syn-theme` | Nested themes recompute semantic tokens locally |
| Density | `data-syn-density="compact\|comfortable\|spacious"` | Adjust padding/control sizing, never shrink body text as a shortcut |
| Visual intensity | `data-syn-intensity="quiet\|standard\|cinematic"` | Applies to optional effects; do not alter interaction/contrast semantics |
| Primary action | `.syn-button.syn-button--primary` | Contrasting `--syn-on-accent` text on `--syn-accent`; predictable hover and focus |
| Content surface | `.syn-panel` | Background and border follow active theme |
| Tables | `.syn-table` | Header associations, real data cells, meaningful overflow behavior |
| Native semantic mode | `.syn-root.syn-semantic` + `syntyr.semantic.css` | Opt-in class-free markup; no blanket global resets |
| Optional effects | `syntyr.effects.css` | No critical information encoded only in a glow, scanline or animation |

For **each interactive component**, cover default, hover (where meaningful), focus-visible, active/pressed, disabled, loading/busy and invalid states where applicable. Prefer native `:disabled`, `:user-invalid`, `required`, and semantic ARIA states such as `aria-invalid`, `aria-expanded`, `aria-current`, and `aria-busy`. Use custom `data-*` only for presentation metadata. Do not invent fake disabled or loading semantics with opacity alone.

## Zero-JavaScript baseline

Static design, themes, basic disclosure via `<details>`, native `<dialog>` and `popover`, forms and keyboard-focusable controls must not require Syntyr JavaScript. Applications handle actual state changes, form submission, validation, routing, data fetching and server operations. CSS cannot make an inert demo button functional.

Load `syntyr.core.css` for classes; add `syntyr.semantic.css` only if using `.syn-semantic`; add `syntyr.effects.css` only for opt-in decoration. Avoid loading `syntyr.all.css` alongside its constituent CSS files. The consumer does not need Python; Python is a maintainer-only build tool.

```html
<link rel="stylesheet" href="/assets/syntyr.core.css">
<section class="syn-root" data-syn-theme="studio"
         data-syn-density="comfortable" data-syn-intensity="quiet">
  <article class="syn-panel">
    <h2 class="syn-heading">Campaign overview</h2>
    <p>Review current inventory and billing.</p>
    <button type="button" class="syn-button syn-button--primary">
      View campaigns
    </button>
  </article>
</section>
```

This example demonstrates visual structure, **not** a wired click action.

## Accessibility and motion

- Target WCAG 2.2 AA: at least 4.5:1 contrast for normal text, 3:1 for large text and meaningful non-text boundaries. Evaluate **all** pairs in every palette and state, especially `--syn-accent` with `--syn-on-accent`, primary hover, muted text and nested overrides. A token's name alone does not establish contrast.
- Retain visibly distinct `:focus-visible` outlines. Never suppress native keyboard access or substitute a color-only state indicator. Confirm keyboard order, accessible names, headings, input labels, status text and error announcements in application context.
- Respect `prefers-reduced-motion` and `forced-colors`. Decorative gradients, grid backgrounds, scanlines and glows should degrade without removing essential affordances. Test `prefers-contrast: more` where supported.
- Support 200%/400% zoom and narrow-screen reflow, including long translated labels, dense tables and focus targets. Use responsive containers rather than rigid viewport assumptions where practical.
- Keep ordinary SaaS pages at `quiet` or `standard` visual intensity. Reserve `cinematic` for deliberate marketing/demo regions; respect explicit user preference over spectacle.

## AI-agent implementation rules

1. Determine the **installed Syntyr version** and available CSS modules before selecting a pattern. Alpha.5 examples may not work with alpha.4.
2. Begin with valid semantic HTML and real content. Apply `.syn-root` and existing `syn-` classes; never create global styles that leak outside a Syntyr scope.
3. Choose Studio for neutral admin and documentation experiences. Use Grid/Noir only where the product brief explicitly warrants them. Do not infer a preference for cyberpunk styling on every page.
4. Use existing token roles, component recipes and data attributes before adding arbitrary one-off values. Do not invent `--syn-*` tokens or class names without checking source/docs.
5. Check every required component state, accessibility mode and light/dark boundary. Prefer real keyboard and browser validation to screenshot similarity.
6. Ship functional HTML and application wiring. Explicitly label illustrative/static behaviors in examples; do not claim CSS implements business logic.
7. Keep runtime JavaScript and network assets optional. Do not add React, Tailwind, CSS-in-JS, remote icons, custom fonts or client-side hydration solely to style Syntyr components.
8. Keep external design references conceptual. **Do not copy** recognizable third-party branding, layouts or licensed assets into Syntyr.

## Change control and validation

Update `src/tokens.css` first, then sync this file. Add or update focused tests before changing component behavior. Run the project's Python contract tests, regenerate distributions when CSS changes, then run browser accessibility checks appropriate to the affected feature. Changing this file alone must not change shipped CSS.

```sh
python3 scripts/sync_design_md.py
python3 scripts/sync_design_md.py --check
python3 -m unittest discover -s tests -p 'test_*.py'
```
