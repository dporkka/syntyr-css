Using Syntyr with coding agents

Syntyr works with ChatGPT, Codex, Claude Code, Cursor and other agents that generate HTML or framework markup. No Syntyr-specific service, account, MCP server or runtime JavaScript is required.

Recommended context to supply an agent

  1. Specify the exact Syntyr release and CSS modules installed (published 0.3.0-alpha.4 versus unreleased source 0.3.0-alpha.5).
  2. Link to AI quickstart and the relevant component reference. If the agent can fetch websites, include /llms.txt.
  3. For complex UI, supply recipes, framework integrations and the component manifest. For unreleased alpha.5 source-only form patterns, use copy-owned form recipes and the optional Radix styling adapter; do not attribute these to published alpha.4.
  4. Ask it to state which stylesheets it used, avoid undocumented classes and verify keyboard/form semantics.

Suggested prompt for an existing application:

Use Syntyr CSS to build a responsive, accessible account dashboard. My app uses the published v0.3.0-alpha.4 core and recipes CSS, with Studio as the theme. Read the Syntyr AI quickstart and relevant component docs. Generate semantic HTML compatible with my framework. Use only classes present in those stylesheets; if a needed component is unavailable, compose native HTML with application CSS instead. Keep data, auth and actions in the host app. Return the necessary markup, CSS links and a list of any custom styles.

Project-level integration

A consumer may copy agents/syntyr/SKILL.md as an optional local skill in agent tooling that supports Skills. It is a portable instruction document, not a published package, automatic installation, or guaranteed discovery mechanism.

The repository's root AGENTS.md guides agents contributing to Syntyr itself. It does not automatically become instructions in a separate application repository.

Optional skills CLI distribution

The existing MIT-licensed consumer Skill can also be discovered and installed with the third-party skills CLI. There is no separate Syntyr skill package to maintain. From your application directory, inspect the canonical Skill before choosing a project-scoped installation:

npx skills@1.9.0 add https://github.com/dporkka/syntyr-css/tree/main/agents/syntyr --list
npx skills@1.9.0 add https://github.com/dporkka/syntyr-css/tree/main/agents/syntyr --skill syntyr

The commands above pin the verified Skills CLI 1.9.0, which requires Node.js 22.20.0 or later and network access for this optional installation route only. Review the source and select your agent when prompted; do not install globally by default. For reproducible updates, review a specific source commit and use that Git ref instead of the moving main branch. The Skill installs instructions, not CSS, a pinned selector inventory, Syntyr tooling, or an application runtime. It does not change the installed CSS release or grant access to premium assets. Inspect your actual stylesheets before generating HTML; use the offline setup below when you also need release-pinned assets and a local reference. Automatic listing or ranking on skills.sh is not guaranteed.

Offline first-run agent setup (source checkout)

An optional Python standard-library command installs a portable consumer Skill, release-pinned CSS, and a small verified selector reference into an existing app. It runs from a Syntyr source checkout and does not install any application runtime dependencies, connect to services, or publish a package:

python3 scripts/syntyr_agent.py init --project /path/to/my-app --json
python3 scripts/syntyr_agent.py info --project /path/to/my-app --json
python3 scripts/syntyr_agent.py check --project /path/to/my-app --json /path/to/my-app/page.html

init defaults to the published, immutable alpha.4 CSS and writes syntyr.agent.json, versioned CSS files under vendor/syntyr/<release>/, and .agents/skills/syntyr/SKILL.md plus references/api.json. Rerunning is idempotent. Different existing files or symlinked output paths are rejected without overwriting project content. For tooling that expects another skill location, specify --agent claude or --agent cursor; --agent codex and --agent generic use the portable .agents/skills/ path. Projects must still load the copied CSS in their own HTML/framework entrypoint: installation does not silently modify application code or guarantee CSS integration.

Choose --release 0.3.0-alpha.5 only when deliberately testing the unreleased source candidate. The generated api.json lists selectors actually present in the selected CSS files; source-only selectors cannot appear in an alpha.4 reference.

info is read-only project discovery for coding agents. It reports the configured release (published or source candidate), its actual pinned CSS asset hashes and integrity statuses, supported themes, and portable Skill/reference paths. Exit code 0 means the pinned installation is healthy, 1 means degraded or invalid, and 2 means the project was not initialized. Do not infer active stylesheet imports or framework support from this inventory: the host application must still load and test the appropriate CSS. The command does not scan application code or need application dependencies.

check validates the installed CSS asset hashes and literal .html files\nagainst that project's pinned release, returning structured, source-located JSON diagnostics. Its exit codes are 0 for checked and error-free HTML, 1 for errors, and 2 for incomplete coverage (for example, JSX/TSX or no HTML files). It is not a React/Vue/Svelte parser or a browser accessibility test. Generated CSS assets are not proof that the app has actually imported them. The separate local MCP adapter remains available for smaller markup fragments and interactive catalog queries.

Optional local MCP adapter

An optional read-only local MCP server can now expose the checked-in component catalog and CSS API to supported coding agents. It is not needed to use Syntyr CSS, is not installed by the npm package, and does not expose a hosted endpoint. See the MCP adapter source and installation guide for the separate Python SDK installation, version-safe tools, and limits. It defaults to the published immutable 0.3.0-alpha.4 CSS rather than silently offering source-only 0.3.0-alpha.5 selectors. The read-only validate_markup tool reuses the static checker for source-located, machine-readable errors, available class suggestions, and valid theme/state values. Responses are constrained to the selected release's checked-in CSS rather than presenting candidate-only selectors as fixes.

Documents and machine-readable inventory

  • llms.txt: small navigation file following the community llms.txt convention; it is useful when deliberately retrieved, but not a universal automatic-discovery protocol.
  • llms-full.txt: generated, version-stamped concatenation of selected public technical docs, for tools that benefit from one context file.
  • metadata/components.json: small curated, non-exhaustive inventory with the CSS modules required by the included classes. Do not infer that a class is unavailable solely because this catalog omits it.
  • metadata/syntyr-contract.json: full source-discovered Syntyr classes, tokens, known stylesheet distributions, themes, literal state values and curated component recipes. This candidate-version manifest is suitable for LLM tooling and optional static HTML checks; it is not a compiler or an accessibility certification.

Documentation follows the current source candidate; always check release boundaries and the distribution guide before using candidate-only features.

Documentation formats: HTML for people, Markdown for agents

Every approved public guide is published at two stable paths. Use the readable HTML page (for example, /docs/components.html) in browser navigation, search results and links to end users. Use the original Markdown (/docs/components.md) for coding-agent retrieval, repository editing and llms.txt references. The complete HTML guide directory is the human entry point. Both formats contain the same authored guide content; the HTML is rendered ahead of time, not by client-side JavaScript.

These are different representations of the same public documentation, not user-agent cloaking. Anyone can request Markdown directly; agents can also read HTML. Markdown responses have a text/markdown content type and X-Robots-Tag: noindex so search engines favor HTML, while robots.txt and the sitemap advertise public HTML pages. Do not disallow Markdown in robots.txt: agents need to fetch it explicitly. HTML has canonical URLs and points back to its Markdown source via rel="alternate" type="text/markdown".

When adding a guide for public consumption, review the explicit PUBLIC_DOCS allowlist in scripts/build_cloudflare_site.py. Regenerate the committed HTML with the maintainer-only generator (python3 scripts/build_doc_pages.py), and verify it with --check. The core static-site and CI builds require no Markdown parsing package or client runtime.

Validation and maintenance

The repository uses Python standard-library scripts:

python3 scripts/build_agent_docs.py --check
python3 scripts/build.py --check
python3 -m unittest discover -s tests -v
python3 scripts/build_cloudflare_site.py --check

The consolidated reference is deterministic and checked in CI through the Python test suite. The Cloudflare publisher uses a strict allowlist, so exposing new documentation does not expose internal files or business planning documents.

What Syntyr does not do

Syntyr styles browser HTML/CSS. It does not supply a JavaScript component runtime, chart rendering engine, AI API, CRUD handlers, form submission or remote data access. The optional local read-only MCP adapter is a separate developer tool, never a CSS runtime dependency. Use your existing application technology for those responsibilities.
