Syntyr with static-site generators

Syntyr's distribution is ordinary, scoped CSS. It does not require a JavaScript runtime, hydration, Sass, PostCSS, browser-specific components, or a static-site generator integration package. Generate semantic HTML with your preferred template engine; load one CSS distribution from your site's assets and put syn-root on the intended page or region.

Version boundary: the source repository currently contains an unreleased alpha.5 npm package and CSS candidate. The published alpha.4 assets are different. Do not claim npm install @syntyr/css will fetch alpha.5 from the registry; use an actual published, pinned version, a local package archive, or a self-hosted versioned CSS file.

Runnable zero-JavaScript marketing site starter

The Waypoint SaaS marketing starter demonstrates how one Syntyr stylesheet can serve a complete three-page site: a home page with hero, dashboard illustration, feature grid, workflow steps and native FAQ; a pricing page; and an about page. All content is explicitly fictional. Unlike a source-only snippet, it includes an offline exporter:

python3 scripts/export_site_starter.py --output /tmp/waypoint-static
python3 -m http.server 8000 --directory /tmp/waypoint-static

Open http://localhost:8000/. The export contains its own pinned assets/syntyr.core.css, works offline, and uses no browser JavaScript. The public preview is available only after the corresponding source change is published. It is a starting point for Astro, Hugo or Eleventy composition, not a prebuilt adapter for any generator. The source candidate remains unreleased.

The separate marketing-site deployment guide adds isolated Vercel and Netlify Git-project settings, plus Render, Cloudflare, GitHub Pages and ordinary static-server instructions. Build repeatably with python3 scripts/build_saas_marketing_site.py, then publish only deploy/saas-marketing/.public (nine allowlisted files). This is separate from the repository-root SaaS Admin deployment and does not add a runtime. The example remains noindexed until its fictional content is replaced.

If you are not using a Node build, copy the exact released stylesheet into your static asset directory. No npm dependency is needed. For pure HTML and native elements, choose syntyr.semantic-bundle.css instead of core and opt in with class="syn-root syn-semantic". For explicit components, load syntyr.core.css once and use classes such as syn-panel and syn-button. Do not combine a bundle with its constituent CSS.

Astro

---
// examples/astro uses a local file:../.. development dependency.
import '@syntyr/css/core.css';
---
<main class="syn-root syn-page" data-syn-theme="studio">
  <h1 class="syn-heading">Static Astro page</h1>
</main>

The import is build-time CSS processing; no Syntyr script is injected. To publish under a subdirectory, set base: '/my-project/' in astro.config.mjs. Do not hardcode href="/assets/..." unless you also account for import.meta.env.BASE_URL. See Astro's CSS guidance and base-path configuration.

Eleventy

The Eleventy example copies the current core and recipes CSS directly to _site/assets/. The independent Nunjucks template renders the same validated CMS JSON as the Hugo and Astro/Keystatic examples. For CSS delivery and the scope, it uses:

<link rel="stylesheet" href="{{ '/assets/syntyr.core.css' | url }}">
<main class="syn-root" data-syn-theme="studio">
  <h1 class="syn-heading">Static site</h1>
</main>

pathPrefix: '/syntyr-eleventy/' deliberately tests a project-pages base path. Adapt it to your hosting path. No client-side Eleventy JavaScript is needed. Eleventy's URL filter documents subpath behavior.

Hugo

Copy dist/syntyr.core.css to static/assets/syntyr.core.css, or use a filesystem mount as in the Hugo preview. In a Hugo layout:

<link rel="stylesheet" href="{{ "assets/syntyr.core.css" | relURL }}">
<main class="syn-root" data-syn-theme="studio">...</main>

Do not use an unprefixed /assets/... URL for GitHub Pages project sites. For an independent, CMS-driven landing page, the runnable Hugo fixture renders the same content/pages/home.json as the Git-backed CMS starter, with five native semantic HTML blocks and no browser script:

python3 scripts/build.py
python3 scripts/build_hugo_cms_starter.py --hugo hugo --output /tmp/syntyr-hugo-site

It verifies generated CSS and page URLs under /syntyr-hugo/ and supports --base-url https://example.com/my-project/. Hugo is a build-time tool, not a requirement of the Syntyr CSS package.

Hugo's own preview script validates its existing rendered Markdown pages and local links:

python3 scripts/verify_hugo_preview.py --hugo /path/to/hugo

Soupault: incrementally adopt Syntyr in existing HTML

Soupault can process a handwritten site (or another generator's output) without introducing a new template system. The two-page processor fixture injects a self-hosted semantic bundle using a head selector:

[settings]
  generator_mode = false
  clean_urls = false

[widgets.syntyr-css]
  widget = "insert_html"
  selector = "head"
  html = '<link rel="stylesheet" href="/syntyr-soupault/assets/syntyr.semantic-bundle.css">'
  parse = true

Opt in only on the region you intend to style, using class="syn-root syn-semantic". Keep existing host styles and behavior. The processor does not infer ARIA, rewrite component markup, sanitize HTML, or add a runtime. Do not inject a second Syntyr bundle into a page that already loads one. See the fixture README for installation, commands and the nested-route checks.

Jekyll / GitHub Pages

Jekyll needs only a copied prebuilt asset and native Liquid URL filtering. In a consumer Jekyll site's root:

mkdir -p assets/css
cp /path/to/syntyr/dist/syntyr.core.css assets/css/syntyr.core.css

In a layout or page (not inside a verbatim Liquid/raw block):

<link rel="stylesheet" href="{{ '/assets/css/syntyr.core.css' | relative_url }}">
<main class="syn-root" data-syn-theme="studio">...</main>

If the site lives at https://user.github.io/project/, set baseurl: "/project" in _config.yml. Commit the CSS asset with your site. Do not put front matter in the CSS file or run it through Jekyll's Sass compiler. Jekyll's GitHub Pages guide explains relative_url.

Zola

In the consumer site's root:

mkdir -p static/assets
cp /path/to/syntyr/dist/syntyr.core.css static/assets/syntyr.core.css

In a Tera template:

<link rel="stylesheet" href="{{ get_url(path='assets/syntyr.core.css') }}">
<main class="syn-root" data-syn-theme="studio">...</main>

Set base_url = "https://example.com/project/" in config.toml for subpath hosting. This URL is resolved at build time; Syntyr does not need client JavaScript or a Zola-specific adapter. See Zola's get_url.

Next.js export, Gatsby and documentation generators

Next.js supports a static-export deployment using output: 'export' in next.config.*. Import one Syntyr CSS file from the top-level App Router layout and apply syn-root in HTML. Adjust basePath and static assets when exporting to a project subpath. Next.js/Gatsby may ship their own hydration JavaScript: "zero Syntyr runtime JS" does not mean a zero-JS site when the generator itself uses client-side code. Gatsby, VitePress and Docusaurus can consume the same CSS through their respective global style entrypoints; these are integration instructions, not verified build fixtures.

Shared CMS rendering contract

The Python standard-library renderer is the reference for the existing portable CMS v1 JSON. Independent Hugo, Eleventy and Astro/Keystatic templates consume the same content. This is not a new template language, a new content schema, or a CSS runtime dependency.

The Python renderer, Hugo staging, Eleventy configuration, Keystatic/Payload exports and parity builders/verifiers share the canonical strict JSON loader. It rejects duplicate object keys, invalid UTF-8/Unicode, non-finite numbers, inputs larger than 16 MiB and excessive nesting before page validation. Use python3 scripts/render_cms_starter.py --validate-only for read-only preflight; it does not render or publish anything. These are build-time content checks, not a live upload security boundary.

Their optional build verifiers compare the generated landing page against the reference: ordered native HTML elements, decoded text, headings and anchor IDs, ARIA and Syntyr classes, theme, metadata and link targets. Formatting, class order, optional paragraph/list end tags and bundler CSS filenames may differ. The checker rejects unprefixed local links, missing core/recipe CSS markers and executable HTML scripts. It is a narrow regression contract, not an HTML5 parser, full CSS validator or browser accessibility test.

python3 scripts/build_hugo_cms_starter.py --output /tmp/syntyr-hugo-parity
npm run build --prefix examples/eleventy
npm run verify --prefix examples/eleventy
npm run build --prefix examples/astro-keystatic
npm run verify --prefix examples/astro-keystatic
python3 -m unittest tests.test_cms_generator_parity -v

Install the optional generators/fixture dependencies first. Set HUGO_BIN and SOUPAULT_BIN to local executables to exercise binary-based tests; Node fixtures' real-output tests require their builds. Without optional tools those tests skip, while stdlib contract tests still run. The Soupault fixture intentionally checks preservation of handwritten source rather than treating it as a fourth CMS template engine.

Automated fresh-build browser parity

The opt-in .woodpecker/static-generators.yaml gate executes for relevant pull requests and main pushes, plus manual/tag runs. A pinned Linux/amd64 Hugo release is checksum-verified before execution, and Eleventy, Astro and the development-only Playwright driver use their checked-in npm lockfiles. The builder creates four fresh outputs and never uses a previous _site or dist directory.

From the repository root, with Node.js, Python and a reviewed Hugo binary:

npm ci --prefix examples/eleventy --no-audit --no-fund
npm ci --prefix examples/astro-keystatic --no-audit --no-fund
npm ci --prefix examples/lit --no-audit --no-fund
python3 scripts/build_generator_parity.py --hugo /path/to/hugo --output /tmp/cms-parity
node examples/lit/generator-parity-browser.mjs /tmp/cms-parity chromium firefox webkit

The output location must not exist. The first command sequence checks each independent renderer against the canonical CMS JSON (including Astro data drift), then stages verified HTML/CSS into an isolated directory. The browser command serves only built HTML/CSS, uses each generator's actual deployment mount, disables application JavaScript, blocks external requests, and exercises keyboard skip links, a local section link and native disclosures. It compares full-page PNGs against the Python reference in the same browser run at 320, 390 and 1280 pixels: 27 pairwise comparisons when all three engines are available. It uses no platform-dependent golden images. Missing browser binaries or a broken fixture are failures, not skipped passes in this gate.

Browser binaries and OS dependencies are maintainer tooling, not shipped to Syntyr consumers. The pinned Woodpecker browser image supplies them. Local installations can use Playwright's supported installation procedure; an explicit SYNTYR_CHROMIUM_EXECUTABLE, SYNTYR_FIREFOX_EXECUTABLE or SYNTYR_WEBKIT_EXECUTABLE selects an already-installed compatible binary. This tests visual and semantic equivalence, not accessibility conformance, and cannot substitute for the separate human release gate.

Verification and failure modes

From the Syntyr repository root:

python3 scripts/build.py --check
python3 -m unittest tests.test_static_site_generators tests.test_adoption_starters
cd examples/eleventy
npm ci
npm run build
npm run verify

The optional Python verifier checks generated HTML, not merely source templates. It rejects missing/local-unresolvable stylesheets, stylesheet URLs that ignore the deployment base path, unexpected browser scripts, missing syn-root scopes, and CSS output without Syntyr selectors. For a different generator, point it at its output and pass its exact mount prefix:

python3 scripts/verify_static_generators.py /path/to/site-output --base-path /my-project/

Only run it against pages deliberately built to be JavaScript-free and styled with Syntyr; it is not a general-purpose validator for unrelated application routes. It checks output correctness but not browser accessibility, responsive layout, static exporter security settings, or hosting/CDN rewrite behavior. For a visual smoke test, serve the generated output at its configured base path and inspect styles/network requests in an actual browser.

Common pitfalls: using a root-absolute CSS URL on a subpath deployment; importing core plus the semantic bundle (duplicate styles); applying syn-semantic globally to an existing third-party theme; unpinned remote CDN URLs; and assuming file:../.. in a development fixture is a published npm package. The Syntyr CSS runtime remains zero dependency regardless of the generator chosen.
