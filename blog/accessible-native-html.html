Accessibility / FIELD NOTES

Accessible interfaces start with native HTML, not ARIA patches

Build resilient forms, links, disclosures, and layouts with browser semantics and Syntyr's progressively enhanced CSS.

Syntyr team · November 16, 2026

Accessibility problems often begin when a familiar browser element is replaced with a custom imitation. A clickable <div> does not acquire button semantics just because it has a click handler. Native HTML already implements much of the interaction contract that products otherwise rebuild.

Choose an element for its job

Use <a href> for navigation, <button> for actions, <label> for form controls, and <details> with <summary> for simple disclosures. These choices preserve expected keyboard behavior without requiring a JavaScript widget runtime.

Syntyr styles those elements through small opt-in classes. The underlying DOM remains plain HTML, so a server-rendered document still works if client scripts fail or never load.

A form that keeps its native contract

<form class="syn-root" action="/contact" method="post">
  <label class="syn-label" for="email">Work email</label>
  <input class="syn-input" id="email" name="email"
         type="email" autocomplete="email" required>
  <button class="syn-button syn-button--primary"
          type="submit">Contact us</button>
</form>

The browser supplies basic required-field and email-format validation. Your server must still validate and authorize the submitted data. The CSS library does not provide storage, confirmation email, or application security.

Navigation and focus are content, not decoration

Give each page a main landmark, a meaningful heading hierarchy, and a visible keyboard focus state. Navigation should contain links to real destinations. When a disclosure is hidden, its contents should not remain unexpectedly reachable with the keyboard.

Skip links reduce repeated navigation for keyboard users. Breadcrumbs provide another predictable route through content, particularly in documentation and multi-page blogs. They should use a real navigation landmark with an accessible label and an ordered list.

Test the actual browser behavior

  • Navigate from the address bar through the page with Tab and Shift+Tab.
  • Zoom to 200% and 400% and check reflow without horizontal page scrolling.
  • Check forced-color modes and reduced-motion preferences.
  • Use a screen reader to verify labels, headings, and landmark order.
  • Run automated audits, then perform manual keyboard and content checks.

Native elements reduce the amount of interaction code you need to maintain; they do not eliminate the need to test your content and workflows. See Syntyr's accessibility guidance and browser API patterns for practical constraints and examples.
