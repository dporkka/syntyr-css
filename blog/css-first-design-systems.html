CSS-first vs. JavaScript-first design systems: choosing the right foundation

Where should the design system end and the application begin? A practical guide to CSS-first architecture, dependencies, and maintenance.

Syntyr team · November 16, 2026

A design system can be a collection of reusable presentation rules or an entire component runtime. Those are different responsibilities. Choosing between them changes how many dependencies an application inherits, how easily a team can change frameworks, and which browser behaviors it can use directly.

Separate design from behavior

CSS-first systems define tokens, typographic scales, layouts, and visual treatments that work with ordinary HTML. They can style markup rendered by a static generator, server template, web component, or React application. JavaScript-first systems typically add components that own markup, internal state, and behavior.

Neither model makes accessibility automatic. A native <button> retains its keyboard and activation semantics; a complex combobox still needs careful focus management, labeling, and testing regardless of its styling library. The valuable boundary is the one that assigns behavior only where behavior is necessary.

Compare the tradeoffs

Architectural considerations, not performance guarantees
ConcernCSS-firstJS-first
Static HTMLStyled directlyMay require hydration or framework rendering
Stateful widgetsApplication or optional adapter owns logicOften bundled in component primitives
Framework changesStyle classes can travel with HTMLComponent APIs may need migration
MaintenanceCSS and browser behavior remain primaryRuntime and framework versions need tracking

CSS-first is most compelling for sites that render on the server, content-rich products, and teams that want a small dependency graph. A JavaScript component library earns its cost when accessible, stateful controls would otherwise be repeatedly implemented and maintained by every team.

Start with a small, composable contract

Syntyr makes its visual API explicit through syn-* classes and --syn-* tokens. Load core CSS, then opt into marketing-oriented recipes only for the pages that need them:

<link rel="stylesheet" href="/dist/syntyr.core.css">
<link rel="stylesheet" href="/dist/syntyr.recipes.css">
<section class="syn-root" data-syn-theme="studio">
  <div class="syn-feature-grid">
    <article class="syn-feature-card">…</article>
  </div>
</section>

The example URLs are relative to a self-hosted copy of the Syntyr distribution. In production, pin a versioned release rather than silently inheriting changes from an unversioned asset.

A useful decision rule

Begin with semantic HTML and CSS when browser-native behavior meets the requirement. Add narrowly scoped JavaScript when it creates material value, such as asynchronous search or a multi-step transaction. If a widget needs a full accessibility and state machine, use a well-tested optional adapter rather than reimplementing it casually.
